HLD / Use case / 03

Design
Elasticsearch.

From a search request to capacity planning: indexing, sharding, replicas, aliases, latency, and the safe operating envelope of a production search cluster.

1. What Elasticsearch is

Elasticsearch is a distributed search and analytics engine for workloads needing fast, flexible search over continuously changing data: product catalogs, logs, help-center content, monitoring, security events, and documents.

It stores JSON documents and builds an inverted index for text. Instead of scanning every record, a term maps directly to documents containing it.

{ "title": "Wireless noise cancelling headphones" }

wireless → [document 123]
noise    → [document 123]
cancell  → [document 123]
headphon → [document 123]

Built on Apache Lucene, it adds distributed storage, REST APIs, replication, failover, cluster management, and aggregations. It is usually a read model, not the authoritative system of record.

Primary database / event stream  →  indexing pipeline  →  Elasticsearch

2. Why use Elasticsearch?

  • Full-text relevance: words, phrases, synonyms, prefixes, misspellings, and related forms.
  • Filtering and sorting: combine text with category, location, permissions, price, or date.
  • Faceting and analytics: counts by brand, price range, region, severity, or time bucket.
  • Near-real-time search: newly indexed data is normally visible within seconds.
  • Horizontal scale: distribute storage and query work across machines.

A relational database remains excellent for inventory, orders, and transactions. Do not use Elasticsearch merely to store JSON or replace transaction processing: it adds operational complexity, needs memory and disk, and is eventually consistent for search visibility.

4. How a document is indexed

PUT /products-v1/_doc/123
{ "title": "Wireless noise cancelling headphones", "brand": "Acme", "price": 4999, "in_stock": true }
  1. Coordinate: a load balancer reaches any healthy node, which reads cluster state and becomes the coordinating node.
  2. Route: Elasticsearch selects the primary shard: shard = hash(_id) mod primary_shards. Custom tenant routing can help locality but may create hot shards.
  3. Index: the primary validates mappings, analyzes text, writes to the translog, adds the change to in-memory buffers, and sends it to replicas.
  4. Acknowledge: replicas apply the operation; the required active copies acknowledge according to wait_for_active_shards.
  5. Refresh: a new Lucene segment is opened for search, often about every second on active indices.
  6. Flush and merge: immutable segments merge later and old translog operations are discarded; this background I/O and CPU needs headroom.

Near-real-time: write accepted → translog protects operation → refresh → document becomes searchable.

Do not force refresh after every write: it makes many small segments and harms ingest throughput.

5. How a search request works

GET /products-search/_search
{ "query": { "bool": { "must": [{ "match": { "title": "wireless headphones" }}], "filter": [{ "range": { "price": { "lte": 5000 }}}] }}, "aggs": { "brands": { "terms": { "field": "brand.keyword" }}}}

Scatter: the coordinating node resolves the alias, selects one active copy of every required logical shard, and queries them in parallel. Each copy analyzes the query, retrieves candidates, applies filters, scores with BM25, and returns partial aggregations.

Gather: the coordinator merges local candidates into globally sorted results, fetches stored source for the top documents, merges facets, and returns the response.

A broad search can touch every shard. More shards do not automatically make search faster; they add request overhead, queueing risk, memory use, and merge work.

6. Sharding: why, when, and how much

Shards let an index exceed the capacity, recovery time, or write throughput of one node. Choose primary-shard count before large-scale writes; changing it generally means reindexing, splitting under conditions, or creating a new time-based index.

  • Add primaries for data volume, write throughput, or to use available data nodes.
  • Avoid many tiny shards: every shard consumes metadata, file handles, memory, caches, and coordination work.
  • A practical first target is often tens of GB per primary, then benchmark with real documents and queries.
900 GB primary data ÷ 30 GB target per primary ≈ 30 primaries

For time-series workloads, use data streams or time-based backing indices and roll over by age, document count, or primary-shard size instead of one permanent giant index.

7. Replicas: availability and read scaling

total shard copies = primary shards × (1 + replicas)
6 primaries × (1 + 1 replica) = 12 shard copies

Use at least one replica when the data must stay available after a node failure. Replicas also distribute concurrent reads. Increase them when read QPS or fault tolerance is the bottleneck; they are not backups because logical mistakes replicate too. Use snapshots to object storage.

Elasticsearch never places a replica on the same node as its primary. Allocation awareness should also spread copies across zones, racks, or hosts.

Logical shardPrimaryReplica
P0 / R0Zone A, Node 1Zone B, Node 4
P1 / R1Zone B, Node 2Zone C, Node 5
P2 / R2Zone C, Node 3Zone A, Node 6

8. Scaling the cluster

Writes and storage: add data nodes; spread primaries; bulk-index; index only fields that need search/aggregation; tune refresh interval and merge pressure during ingest-heavy periods. Adding nodes will not improve write parallelism if an index has too few primaries.

Reads: add replicas and data nodes, reduce query scope with filters/routing/time bounds, optimize mappings and aggregations, and cache stable filters. Replicas help concurrency; one request still generally needs one copy of each logical shard.

Separate roles: three dedicated cluster-manager nodes protect cluster state and quorum; data nodes store and search/index; coordinating-only nodes handle heavy scatter/gather traffic; ingest nodes run enrichment/transforms. Keep cluster managers away from unpredictable aggregations and ingest.

9. Aliases: stable names for safe changes

An alias separates the application’s stable name from physical index names, enabling rebuilds, versioning, rollover, and migration without synchronized application deployment.

  1. products-search points to products-v1.
  2. Create products-v2 with a better mapping or analyzer.
  3. Reindex from the source of truth or v1; validate counts, relevance, and latency.
  4. Atomically switch the alias to v2.
Before: products-search → products-v1
After:  products-search → products-v2

For events, use a write alias for the active backing index and a read alias for historical indices. Roll over on size, age, or document threshold to make retention practical.

events-write → events-2026.09.23-000001
events-read  → events-2026.09.01-*

10. Latency: concepts people often miss

Track p50, p95, and p99 for indexing and search. A distributed query is constrained by its slowest shard: the tail-at-scale problem.

search latency = network + load balancer + coordination queue
               + slowest shard query + fetch + merge + serialization

index latency = request queue + primary indexing + replication + acknowledgement

High search latency commonly comes from too many shards, wildcard/script/nested/deep-pagination queries, high-cardinality aggregations, slow disks, low filesystem cache, CPU saturation, GC, queues, recovery, merges, hot shards, or network hops.

  • Use filters for time, tenant, category, and geography.
  • Use search_after or point-in-time pagination—not deep from + size.
  • Bound user-controlled wildcard, regex, and aggregation requests.
  • Use keyword subfields for exact filters/aggregations and text fields for full text.
  • Keep heap conservative and leave RAM for OS filesystem cache.
  • Benchmark realistic data, query mix, concurrency, and failures.

11. Capacity envelope: a first-pass estimate

Capacity envelope means the safe range of document count, storage, ingest rate, query rate, and latency where the cluster still meets SLOs with recovery headroom.

InputExample
Documents ingested/day20 million
Average raw document1 KB
Retention90 days
Index expansion1.4×
Replicas1
Search load300 average / 900 peak QPS
Index load250 average / 800 peak docs/sec
Search SLOp95 < 200 ms
  1. Raw retained data: 20M × 1 KB × 90 = 1.8 TB. Use sampled documents because large fields and arrays skew averages.
  2. Primary index: 1.8 TB × 1.4 = 2.52 TB. Measure expansion; inverted indexes, doc values, source, mappings, and stored fields matter.
  3. Replicas: 2.52 TB × (1 + 1) = 5.04 TB.
  4. Headroom: reserve 30% for merges, translogs, recovery, relocation, uneven placement, and growth: 5.04 TB × 1.30 = 6.55 TB.
  5. Storage nodes: at 2 TB raw/node and 70% usable, 6.55 ÷ 1.4 = 5 nodes. This is a storage lower bound; validate CPU, RAM, IOPS, and network too.
  6. Primary shards: at 40 GB per primary, 2.52 TB ÷ 40 GB ≈ 63 primaries; with one replica, about 126 copies.
  7. Benchmark: test ingest with replicas, p50/p95/p99 search, CPU/heap/GC/IOPS/network/queues, aggregations, refreshes, merges, node failure, and recovery.

If p95 rises sharply under load, you have reached a queueing or resource limit—not a comfortable operating point. The safe envelope stays below saturation and preserves healing capacity.

12. Replica storage and placement example

Six primaries plus one replica equals twelve shard copies. A balanced placement over six data nodes and three zones could be: D1/A: P0,R3; D2/A: P1,R4; D3/B: P2,R5; D4/B: R0,P3; D5/C: R1,P4; D6/C: R2,P5. Each replica is in a different zone from its primary.

If a primary node fails, a replica is promoted and a replacement replica is built elsewhere. Free disk and network capacity are therefore required for the cluster to heal safely.

13. Interview-ready architecture summary

1. AuthorityDatabase or event stream emits authoritative changes.
2. IndexingService validates, transforms, and bulk-indexes documents.
3. EntryLoad balancer sends clients to coordinating nodes.
4. Write pathCoordinator routes primary writes and replicas.
5. Query pathSearch scatters to copies; hits and facets merge.
6. ResilienceData nodes span domains; three managers coordinate.
7. AliasesStable read/write names protect rollovers and reindexing.
8. RecoverySnapshots protect against disasters and logical mistakes.
9. PlanningStorage, throughput, recovery, and p95/p99 drive capacity.

The core trade-off: more shards improve distribution but add overhead; more replicas improve availability and read capacity but consume disk and increase write work. Build the smallest cluster that meets storage, throughput, recovery, and tail-latency needs with meaningful headroom.
