HLD / Use case / 02

Design
Dropbox.

A simplified file-sync system makes you reason about storage, synchronization, metadata, large-file transfer, concurrency, and reliability at once.

1. What are we building?

Users upload and download files, organize folders, synchronize changes across devices, share files, recover old versions, and transfer very large files. Collaborative editing and full-text search are out of scope for the first design.

2. Start with assumptions

100M registered users20M DAU500 files / active user10 MB average file5 changed files / day3 devices / user5-year retention3 replicas

3. How much storage?

500 files × 10 MB = 5 GB/user
100M users × 5 GB = 500 PB logical data
500 PB × 3 replicas = 1.5 EB raw storage

That scale rules out treating file bytes like ordinary relational-database records. We need distributed object/blob storage.

Metadata store

File ID, user ID, folder, filename, size, version, timestamps, storage location, checksum, and permissions.

Object storage

The actual file bytes: file_123 → 10 MB blob. Metadata tells the system what a file is; blob storage holds it.

4. Upload traffic

20M active users × 5 files/day = 100M updates/day
100M × 10 MB = 1 PB/day logical upload data
≈ 12 GB/sec average incoming bandwidth

Peak bandwidth can be several times higher. File transfer must be distributed and should not pass through application servers.

5. Direct upload architecture

The API handles authentication, authorization, upload-session creation, versions, checksums, and permissions. The client sends the bytes directly to object storage using a pre-signed upload URL or equivalent.

6. Large files need chunking

Split a 10 GB file into independently retriable 4–16 MB chunks. If one chunk fails, resend only that chunk. The client can upload chunks in parallel, resume interrupted uploads, and verify integrity with checksums.

10 GB file→Chunk 1Chunk 2Chunk 3…Chunk N

7. How synchronization works

Each device keeps a local cursor or change token. It asks the metadata service for changes after that cursor, downloads what it needs, then advances the cursor. Push notifications make devices check sooner; the pull-based change log remains the source of truth.

8. Conflicting edits

Use version numbers or content hashes to detect concurrent edits. A safe first version preserves both copies and marks a conflict instead of silently discarding someone’s work.

9. The hard parts

StorageExabyte-scale, durable blobs
BandwidthHigh-volume transfer without API bottlenecks
MetadataBillions of file and version records
SyncReliable change tracking across devices
DuplicatesContent hashes enable deduplication
FailureRetries, checksums, replication, recovery

The interview insight is not the exact number. It is using a rough number to reveal the architectural constraint it creates.
