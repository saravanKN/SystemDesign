1. What Kafka is

Kafka is a durable, append-only distributed log—not a queue that deletes a message after one reader. Producers publish records to topics; Kafka retains them; consumers read by offset; and every consumer group maintains independent progress.

{ "event_id": "evt-8471", "order_id": "ord-123", "event_type": "order_created", "created_at": "2026-09-23T10:00:00Z" }

Order service → orders topic → fulfillment group
                             → analytics group
                             → notification group

This decoupling is Kafka’s core value: downstream systems can be unavailable without blocking the producer.

2. Why use Kafka?

  • Asynchronous workflows: inventory, email, fraud, and analytics react independently after an order is accepted.
  • Traffic buffering: absorb bursts while downstream services work at a sustainable rate.
  • Fan-out: multiple consumer groups receive the same event without repeated producer sends.
  • Replay: new services can read retained history from the beginning or a timestamp.
  • Event-driven architecture and streaming: communicate facts, enrich them, aggregate them, or route them continuously.

A simple queue can be easier for one worker pool and short-lived jobs. Kafka becomes compelling when events remain valuable after delivery, feed many consumers, survive outages, or arrive at sustained high volume.

4. How producing a message works

  1. Choose a partition: Kafka guarantees order inside one partition, commonly partition = hash(key) mod partition_count. Use order_id so created → paid → shipped stays ordered per order.
  2. Send to leader: the producer sends to the chosen partition leader. The leader appends locally and assigns the next partition-local offset.
  3. Replicate: follower replicas fetch the record. The sufficiently caught-up replicas form the in-sync replica set (ISR).
  4. Acknowledge: the producer gets success once its configured durability condition is satisfied; enable idempotence so retrying a network failure does not duplicate a record.

For critical events use acks=all, min.insync.replicas=2, and replication factor 3. Kafka then rejects unsafe writes rather than falsely confirming insufficiently replicated data.

5. How consumers read messages

Consumer groups distribute work: Kafka assigns each partition to at most one consumer within one group. With six partitions, three consumers might own 0–1, 2–3, and 4–5. Extra consumers beyond partition count sit idle, so partitions cap group parallelism.

Independent groups get independent views: fulfillment, analytics, and email groups each read all order events and store their own committed offsets. That enables fan-out and replay.

Offsets and delivery: commit before processing risks loss after a crash; commit after processing gives at-least-once behavior because a crash can reprocess. Exactly-once Kafka read-process-write flows use transactions, but external side effects still require idempotency. Store event IDs or use natural business keys to prevent duplicate payments, emails, or inventory updates.

6. Partitions: ordering, parallelism, and trade-offs

Add partitions for more producer throughput, consumer-group parallelism, or distribution across brokers. Choose a key matching the required ordering boundary: customer_id, order_id, or account_id; omit a key only when no entity order is needed.

A hot customer, tenant, product, or account can overload one leader while the rest of the cluster is idle. Use a better key, isolate extreme entities, or use a composite/salted key only if breaking strict entity-wide ordering is acceptable.

Do not over-partition blindly. Partitions add metadata, files, replication, rebalance work, and may increase latency with many small batches. They are hard to reduce; increasing them changes future key mapping and does not preserve strict key order across the change.

7. Replication, leader election, and failures

Replication factor 3 means three copies on different brokers, ideally different zones. If a leader fails, Kafka elects an in-sync follower; producers refresh metadata and consumers reconnect.

PartitionLeaderFollower 1Follower 2
orders-0Broker A, Zone ABroker B, Zone BBroker C, Zone C
orders-1Broker B, Zone BBroker C, Zone CBroker A, Zone A
orders-2Broker C, Zone CBroker A, Zone ABroker B, Zone B

Replication factor 2 can survive one broker loss with less recovery margin; factor 1 has no broker-failure tolerance. Avoid unclean leader election for critical topics because an out-of-sync replica may lose acknowledged records.

8. Retention and log compaction

Time/size retention keeps historical events for a fixed period, such as clickstreams for seven days or audit events for 365 days, then deletes old segments.

Log compaction eventually retains the latest record for each key—useful for entity state, configuration, feature flags, and Kafka Streams changelogs, not immutable audit trails. Tombstones represent deletion.

customer-123 → { status: "gold" }
customer-456 → { status: "standard" }
customer-123 → { status: "platinum" }  ← latest value retained after compaction

9. Latency and throughput concepts

produce latency = batching wait + network + leader append + follower replication + acknowledgement

end-to-end latency = producer publish + partition wait + consumer poll/process + downstream side effect

lag time ≈ records behind ÷ consumer processing rate

linger.ms and batch.size improve batching and throughput but can add bounded delay. Compression such as lz4 or zstd saves disk/network but consumes CPU; acks=all strengthens durability with potential added latency.

Monitor p50, p95, and p99. Tail latency rises as disk, network, CPU, request queues, or replication bandwidth saturate. A slow follower can shrink ISR and threaten safe write availability. Lag is meaningful only together with the consumer’s processing rate and retention window.

10. Capacity envelope: a first-pass estimate

InputExample
Peak ingress50,000 events/sec
Event size after serialization1 KB
Retention7 days
Replication factor3 total copies
Compression2:1
Producer SLOp95 < 50 ms
Consumer SLOp95 end-to-end < 5 sec
  1. Ingress: 50,000 × 1 KB = 50 MB/sec, or 50 MB/sec × 86,400 ≈ 4.32 TB/day uncompressed.
  2. Compression: at 2:1, leader data is 4.32 ÷ 2 = 2.16 TB/day. Measure real payloads: encrypted and already-compressed data behave differently.
  3. Retention and replication: 2.16 TB/day × 7 days × 3 = 45.36 TB cluster data.
  4. Headroom: reserve 30% for re-replication, uneven partitions, deletion timing, OS space, and growth: 45.36 × 1.30 ≈ 59 TB.
  5. Broker lower bound: at 12 TB raw and 70% usable per broker, 59 ÷ 8.4 = 8 brokers. Validate traffic as well as disk.
  6. Network: ingress is 50 MB/sec; replication traffic is approximately 50 × (3 − 1) = 100 MB/sec. Three groups each reading every event add roughly 50 × 3 = 150 MB/sec consumer egress.
  7. Partitions: if tests prove 10 MB/sec safely per partition, writes need 5; if the main group needs 12 workers, use at least 12, then add measured growth headroom such as 18 or 24.

Do not take a generic per-partition throughput number as fact. Message size, compression, acknowledgements, hardware, and consumer processing determine real safe capacity.

11. A robust production baseline

  • Three or more brokers spread across three availability zones.
  • Replication factor 3, acks=all, and min.insync.replicas=2.
  • Idempotent producers and at-least-once-safe, idempotent consumers.
  • Keys aligned to the ordering boundary; topic-specific retention and compaction.
  • Monitoring for disk, network, ISR shrinkage, under-replicated partitions, controller health, producer errors, and consumer lag.
  • Load tests including bursts, slow consumers, broker failure, and recovery.

3. ReplicateFollowers copy logs across brokers and zones.
4. Acknowledgeacks=all waits for required ISR confirmation.
5. ConsumeGroups read partitions in parallel; groups stay independent.
6. CommitOffsets and idempotency support at-least-once safety.
7. BalancePartitions trade ordering against parallelism and overhead.
8. RecoverReplication and ISR define durability/availability.
9. PlanIngress, retention, compression, replicas, egress, and p95/p99 determine capacity.

Kafka’s central trade-off is simple: keys and partitions provide ordered parallelism; replication provides durable availability. Preserve the order that matters, use enough partitions for measured throughput and consumers, and leave disk/network capacity for a broker or zone failure.
