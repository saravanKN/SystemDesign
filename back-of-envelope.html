HLD / Use case / 01

Back-of-the-envelope
estimation.

A reusable calculation framework for almost any system-design interview. Begin with users and activity, then derive the work your system must do.

Users→Requests→QPS→Storage→Bandwidth→Cache→Machines

1. Start with users and activity

State assumptions explicitly: daily active users (DAU), actions per user per day, read/write ratio, average object size, retention, and the peak-to-average multiplier.

Example: for a URL shortener, assume 100M DAU and 5 redirects per user per day.

100M × 5 = 500M reads/day

2. Convert daily requests to QPS

There are 86,400 seconds in a day; in interviews, use 100,000 for fast mental math.

QPS ≈ requests/day ÷ 100,000
500M requests/day ÷ 100K = 5,000 QPS
Peak QPS at 3× average = 15K QPS

3. Calculate reads and writes separately

If users create 10M new short URLs per day, that is about 100 write QPS. Compared with 5K read QPS, this is a roughly 50:1 read-heavy system—an immediate signal that caching matters.

4. Estimate storage

Use objects per day × size per object × retention. A 1 KB URL record written 10M times a day consumes about 10 GB/day, or roughly 18 TB over five years before replication, indexes, backups, and overhead.

5. Estimate bandwidth and cache

Bandwidth is QPS × response size. At 5K QPS and 1 KB responses, the system needs roughly 5 MB/sec. For cache, identify a plausible hot set rather than treating “80/20” as a law; then include memory overhead and replication.

6. Estimate machines only when useful

For a 100K peak QPS workload, instances safely handling 2K QPS imply a theoretical minimum of 50. Add capacity deliberately for failures, deployments, spikes, and availability-zone loss.
