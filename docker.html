Docker.

Docker packages an application, runtime, libraries, and configuration into a portable image, then runs it as an isolated and disposable container.

1. Why Docker?

Before containers, servers drifted through different libraries, environment settings, and manual fixes. Docker defines one immutable artifact: application code + runtime + OS-level dependencies + startup command. It gives consistent local, CI, VM, and cloud behavior; isolated dependencies; repeatable builds; tag/digest rollback; and a standard unit for Kubernetes.

Docker is not an orchestrator. It runs containers on one host; Kubernetes, ECS, Nomad, or similar systems coordinate them across hosts. Containers share the host kernel, so VMs remain a stronger isolation boundary when required.

3. Image build lifecycle

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node
CMD ["node", "server.js"]
  1. Start from a trusted base image.
  2. Each Dockerfile instruction produces a cached layer.
  3. Tag the result and prefer immutable digests.
  4. CI tests and scans it, then pushes it to a registry.
  5. A host/orchestrator pulls the exact image and starts a container.

Order layers intentionally: copy dependency manifests and install before frequently changing source so dependencies stay cached.

4. Container lifecycle

Image available → create container → start PID 1 → running → stopped / exited → removed or recreated

Docker creates namespaces for processes, network, mounts, and isolation; applies cgroups; mounts read-only layers plus a thin writable layer; configures environment, volumes, and networks; then starts PID 1. When PID 1 exits, the container exits.

On graceful stop, Docker sends SIGTERM, waits through a grace period, then SIGKILL. Applications should stop accepting requests, drain or hand off safe work, close connections, and exit. Restart policies are no, on-failure, always, and unless-stopped; they only recover processes on the same host.

5. How containers communicate

On a user-defined bridge network, Docker DNS resolves container names: web → http://api:8080 → api and api → postgres:5432 → database. Separate networks isolate services unless explicitly connected.

Host traffic uses published ports—host:443 → container:8080—typically through a reverse proxy or load balancer. External calls are normal distributed calls: use TLS, authentication, timeouts, retry/backoff, and observability.

6. Storage: writable layers and volumes

A container’s writable layer disappears with the container. Use volumes or external services for persistent data. Keep binaries and temporary files in the container; use managed databases/object stores or carefully managed volumes for durable production state. Container replicas do not make state durable.

7. Reliability and fault tolerance

FailureDocker aloneProduction approach
App crashMay restart processHealth checks, alerts, restart
Writable layer lostData is lostExternal state / managed volume
Host failsAll host containers disappearReplicas across hosts with orchestrator
Registry unavailableNew pull failsHA registry and cache
Bad releaseNew containers failImmutable digests, staged rollout, rollback

Stateless services need multiple replicas on separate hosts behind a load balancer. Stateful workloads need durable replicated storage and backups.

8. Security essentials

  • Use small, maintained base images and pin versions/digests.
  • Use multi-stage builds so compilers do not reach the runtime image.
  • Run as non-root; restrict capabilities and use read-only filesystems where practical.
  • Inject secrets at runtime; never embed them in Dockerfiles or layers.
  • Scan images and update base images regularly.
  • Do not mount the Docker socket into ordinary application containers.

9. Performance and capacity

Containers have low overhead versus VMs but still share finite CPU, memory, disk, and network. Use resource controls in the orchestrator; an over-limit memory process is commonly OOM-killed. Cold start includes pull, extraction, volume/network setup, and application initialization. Keep images small, cache layers, avoid long startup work, and expose readiness only once serving is safe.

Host RAM = 32 GiB; reserve OS/runtime = 6 GiB
usable application RAM = 26 GiB
measured container peak = 1.2 GiB; 20% margin = 1.44 GiB
safe count = floor(26 / 1.44) = 18 containers

Then validate CPU, disk I/O, and network with load tests.

10. Interview-ready summary

Docker turns an application and dependencies into an immutable image. The runtime creates an isolated container with namespaces, cgroups, networking, and a writable layer, then runs PID 1. Containers are disposable; state belongs outside them. Docker restarts local processes, while multi-host reliability, rollouts, service discovery, and autoscaling need an orchestrator such as Kubernetes.
