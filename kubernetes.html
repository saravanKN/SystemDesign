Kubernetes.

Kubernetes schedules containers across machines and continually reconciles the running cluster with declared desired state.

1. Why Kubernetes?

It solves placement, restarts, scaling, service discovery, load balancing, safe deployments, configuration/secrets, and persistent storage once workloads must run reliably across machines. It adds operational, networking, security, and cost complexity, so a small product may be simpler on managed containers or a VM.

2. Cluster architecture

The control plane contains API server (front door), etcd (durable desired/current state), scheduler (node selection), controller manager (reconciliation), and optionally cloud-controller manager. Each worker has kubelet, a container runtime such as containerd/CRI-O, and kube-proxy/data plane for Service routing.

Desired state in API → controllers observe actual state → controllers create / repair resources

A Deployment asking for three replicas is a continuously maintained goal, not a one-time command.

4. Pod lifecycle: YAML to running application

  1. Submit: user/CI/GitOps sends a Deployment; API server authenticates, authorizes, validates, runs admission, and stores it in etcd.
  2. Reconcile: Deployment controller sees desired replicas exceed actual, creates ReplicaSet and Pod objects. Pods are Pending until scheduled.
  3. Schedule: scheduler filters/scoring nodes by CPU/memory requests, selectors/affinity, taints/tolerations, volume topology, ports, and architecture; topology spread can separate replicas across nodes/zones.
  4. Prepare: kubelet pulls the image, creates pod sandbox/network namespace, calls CNI, mounts volumes/ConfigMaps/Secrets, runs init containers, starts main containers, and reports status.
  5. Serve: startup probes protect slow boot; readiness controls Service endpoints; liveness restarts stuck containers.
  6. Terminate: endpoints are removed, kubelet sends SIGTERM, waits terminationGracePeriodSeconds, then SIGKILL if required.

Containers in a Pod share network namespace and can use localhost/shared volumes. Pod phases include Pending, Running, Succeeded, Failed, and Unknown. Always, OnFailure, and Never define restart policy; deterministic failures become CrashLoopBackOff and need debugging, not extra replicas.

5. How Pods communicate

CNI networking normally gives each Pod an IP and Pod-to-Pod connectivity; never depend on an ephemeral Pod IP. A Service selects Pods by labels and provides stable DNS/virtual IP: checkout → http://payment.default.svc.cluster.local → ready payment Pod. CoreDNS resolves names and the data plane forwards to ready endpoints.

Service types: ClusterIP for internal access, NodePort for a port on every node, LoadBalancer for external/cloud load balancing, and ExternalName for a DNS alias. External HTTP(S) flow is client → cloud LB → Ingress/Gateway → Service → ready Pod. NetworkPolicies restrict which Pods/namespaces/ports communicate when supported by the CNI.

7. Scaling and capacity envelope

HPA changes replicas from CPU, memory, or custom metrics such as QPS or queue depth. Choose the real bottleneck. Cluster Autoscaler adds nodes for unschedulable requests, not instantaneous use; small requests overpack nodes and oversized requests waste capacity.

API peak memory = 1 GiB; 25% margin = 1.25 GiB request
8 GiB node − 2 GiB system reserve = 6 GiB allocatable
floor(6 / 1.25) = 4 Pods per node
12 peak replicas need 3 nodes by memory; resilient design may need 4+ to lose one node safely

Validate CPU, topology spread, rolling-update surge, p95/p99, CPU throttling, memory pressure, disk/network, image pulls, and recovery after node/zone loss.

8. Safe deployments

A Deployment rolling update creates new Pods and removes old ones according to maxSurge and maxUnavailable: new Pod starts → Ready → receives traffic → old Pod terminates. Readiness probes and conservative settings protect user-facing services. Pause/roll back if new Pods do not become ready; use canary or blue-green delivery with traffic splitting for higher-risk releases.

9. Latency concepts people miss

client → load balancer → ingress/gateway → Service routing → Pod
       → downstream Services → database/cache → response

Data-plane overhead is usually smaller than application work and downstream dependencies. Main risks are poor requests/limits, CPU throttling, overloaded nodes, retries, startup/rollout behavior, and failing dependencies. Track p50/p95/p99, errors, saturation, availability, restarts, readiness failures, Pending Pods, node pressure, HPA behavior, and endpoint count. Running does not mean Ready.

10. Interview-ready summary

Kubernetes persists desired state through the API and etcd, then controllers reconcile it. Deployment creates Pods; scheduler chooses nodes; kubelet pulls images, configures network/volumes, and starts containers. Services/DNS replace fixed IPs; readiness controls traffic and liveness restarts stuck processes. True availability needs replicas across failure domains, a resilient control plane, safe rollouts, and external or replicated state.
